HOW TO INSTALL
--------------
1. Back up the current file first. In cPanel File Manager go to

       app/Http/Controllers/Auth/

   right-click LoginController.php, choose Copy, and save it as
   LoginController.php.backup in the same folder. If anything at all goes
   wrong, rename that back and you are exactly where you started.

2. Upload the LoginController.php from this zip into that same folder,
   replacing the current one.

3. Open your .env file (File Manager, site root, turn on "Show hidden files")
   and add this line at the end:

       GOOGLE_DEBUG=on

   Save.

4. Open petaqr.com in a private window and click "Sign in with Google".


WHAT YOU WILL SEE
-----------------
Instead of being dumped back on the login page with no explanation, you will
now get a plain text page telling you exactly what went wrong. Something like:

    Google sign-in failed while talking back to Google.

    Type:    GuzzleHttp\Exception\ClientException
    Message: ...

    ----- WHAT THE SITE ACTUALLY SENT TO GOOGLE -----

    Client ID: ...
    Redirect:  ...
    Client secret length: 35 characters
    Client secret starts: GOCSPX-
    Client secret ends:   [ab12]

    Lines found in .env:
      GOOGLE_CLIENT_ID      1
      GOOGLE_CLIENT_SECRET  1
      ...

Send me that text and I will know precisely what to fix. It is one screen of
text, no need to hunt through logs.

The second half is there because "the value in the file" and "the value the
site actually uses" are not always the same thing. Two things commonly break
that link, and both are visible above:

 - the same key appearing TWICE in .env. Laravel keeps the first one it reads
   and silently ignores every later one, so a new value pasted at the bottom
   of the file never takes effect.
 - a stray space, line break or quote around the value.

The secret itself is never printed. Only its length and the same last four
characters that the Google console already shows you, so you can compare the
two directly.

If instead it just signs you in - then one of the other fixes in this file was
the problem all along, and we are done.


WHEN WE ARE FINISHED
--------------------
Delete the GOOGLE_DEBUG=on line from .env, or change it to GOOGLE_DEBUG=off.
With that line gone the page behaves normally again for your visitors. Nothing
technical is ever shown to a normal user while it is off.


WHAT ELSE THIS FILE FIXES
-------------------------
1. Errors are no longer thrown away. Every failure is now written to
   storage/logs/laravel.log with the tag [GOOGLE-LOGIN], whether debug is on
   or off. Previously a failed Google sign-in left no trace anywhere, which is
   why we had nothing to go on.

2. Administrators can now sign in with Google. The script always sent people
   to /user/dashboard after a Google sign-in, but that page only admits normal
   users - an administrator was thrown straight back out to the login page.
   Admins now go to /admin/dashboard.

3. New Google accounts were being saved with the hash of an empty password.
   The original line was bcrypt($newUser->user_id), and user_id does not exist
   on a new record, so it hashed nothing at all. Now a long random value.

4. New Google accounts are marked as email-verified. Google has already
   confirmed the address, so there is no reason to send them through your
   email verification a second time.

5. If an account already exists with that email address but is not active, you
   now get told so instead of being silently bounced.


WHAT IT DOES NOT CHANGE
-----------------------
Normal email and password login is untouched. So is the admin panel, and so is
everything else in the file. With GOOGLE_DEBUG off, a visitor sees exactly what
they saw before.

FIRST, SOMETHING THAT CHANGED AT GOOGLE'S END

Before writing any of this I checked Google's current documentation rather
than going from memory, and one thing had moved. One Tap now runs through the
browser's own FedCM system. The old data-use_fedcm_for_prompt setting that
every older tutorial tells you to add is now, in Google's words, "deprecated
and will be ignored if used". It is not in this code. Two things follow from
that, and they are worth knowing before you judge whether it works:

 - the prompt is drawn by the BROWSER, not by your site. It appears in the top
   right of the browser window. That is exactly where you asked for it, but it
   also means you cannot restyle it, and I cannot show you a screenshot of it
   from here - it only appears on a real HTTPS domain that Google recognises.

 - it will not appear for everyone. It shows to visitors who are signed in to
   Google in that browser and have third-party sign-in enabled. If you dismiss
   it a few times, Google stops showing it to you for a while - hours, then
   longer. That is Google's cooldown, not a fault. Test in a fresh private
   window, and do not judge it by whether it appears for you on the tenth try.

HOW THE SECURITY WORKS - the part that matters

The popup hands the browser a signed token, the browser posts it to your site.
A token is just text in a POST body, so anyone can send one. What nobody can
do is forge Google's signature on it. So the controller refuses the sign-in
unless ALL of these hold:

  - the signature matches one of Google's current public signing keys
  - the token says Google issued it
  - the token was issued FOR THIS SITE, not another one. Without this check a
    token minted for any other website using Google sign-in would be accepted
    here as a login. This is the check most tutorials leave out.
  - it has not expired
  - the email on it is one Google has itself verified

The name, email and picture are read out of the signed token, never out of
anything the browser sends alongside it.

WHAT I TESTED, AND HOW

Not "it looks right". I installed the whole thing on a local copy of your site
running against a real database, and drove it over HTTP the way the browser
would. 21 checks, all passing:

  A genuine token
    - accepted, account created, person signed in
    - lands on the plans page, same as any brand new account
    - auth_type Google, role_id 2, status 1, marked email-verified
    - the password saved is NOT the hash of an empty string (that is the
      vendor bug we already fixed on the button path)
    - signing in a second time reuses the account, no duplicate

  Every one of these REFUSED, with the visitor left signed out:
    - a token signed with a different key (a forgery)
    - a token issued for a different website
    - an expired token
    - a token where Google had not verified the email
    - a token with the payload edited after signing
    - an unsigned token, alg=none - the classic JWT bypass
    - junk that is not a token at all
    - a wrong CSRF token
  And no account was created by any of them.

The signature checking uses firebase/php-jwt, which is already inside your
vendor folder - it comes with the script. Nothing needs installing, which
matters because you have no shell access.

   Open your OAuth client and add to "Authorised JavaScript origins":
